# Re-anchor local review state through constrained exact context

## Context

Review threads and bookmarks must survive ordinary source edits, Git group transitions, and explicit renames without letting fiew guess where a concern moved. Existing threads store selected diff excerpts and coordinates; bookmarks store only coordinates. Thread status also conflates reviewer resolution with anchor validity, so temporary anchor loss cannot safely preserve reviewer intent.

RFC-0003 resolved the exact matching, path, lifecycle, trigger, and persistence policy for ISSUE-0023.

## Decision

Use one constrained exact-context transition model for review threads and bookmarks.

Validate raw-byte content at the stored location first. If it still matches, retain the anchor regardless of identical content elsewhere. If it does not, search only the same repository-relative path or an explicit Git rename target. Relocate only when the complete context has exactly one match; zero or multiple matches preserve the old location and mark the anchor Outdated.

Line threads and bookmarks store anchored content plus up to three complete source lines before and after it. Bookmarks additionally store the selected byte offset within the anchored line. File threads store an exact whole-change fingerprint: canonical diff bytes and metadata for text, or available blob and metadata identity for non-text changes. Raw bytes are never whitespace- or syntax-normalized.

Line threads may follow one exact unchanged change among Staged, Unstaged, and Untracked groups. No anchor moves to an unrelated path based only on matching content.

Store thread reviewer lifecycle (Open or Resolved) independently from anchor validity (Current or Outdated). Outdated blocks approval but retains reviewer lifecycle; a later exact match restores the remembered Open or Resolved presentation.

Re-evaluate threads only after accepting a complete generation-current Git snapshot. Re-evaluate bookmarks after that refresh and immediately before opening. Apply transitions in memory even if persistence fails, keep them dirty, report failure, and block approval or clean quit until atomic persistence succeeds; do not roll back the accepted Git snapshot.

Repository-root movement requires no reassociation because `.reviews/` and `.bookmarks/` move with the repository and all anchors are repository-relative. Do not infer identity from remotes or matching content.

Exact context is mandatory in the pre-release `fiew.review/v1` and `fiew.bookmark/v1` formats. Purged pre-context development records receive no migration or compatibility path.

## Rationale

Stored-location validation preserves reliable location evidence and avoids false ambiguity. Exact unique relocation within an unchanged logical path handles ordinary line movement and Git staging transitions while explicit rename metadata is the only trustworthy cross-path evidence. Independent lifecycle and validity preserve reviewer authority through temporary anchor loss.

Three surrounding lines align with the unified diff context already presented by fiew and provide bounded, inspectable matching evidence without fuzzy scoring or language dependencies.

## Consequences

- Review and bookmark schemas gain mandatory context and validity fields; thread lifecycle becomes independent.
- Creation paths must capture exact source-side context and file-change fingerprints.
- A shared pure matcher and transition fixtures become the authority for refresh and open-time behavior.
- Persistence failures can leave displayed transitions dirty but can never produce approval or clean quit.
- Similar content in unrelated files, undeclared file moves, whitespace-only similarity, and ambiguous duplicate contexts become Outdated rather than guessed relocations.
- Semantic and heuristic relocation remains deferred.
