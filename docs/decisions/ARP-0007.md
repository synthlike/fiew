# Use reviewer-owned local threads with command-mediated agent replies

> The canonical Markdown storage and `.md` filename portions of this decision are superseded by ARP-0008. The thread model, reviewer authority, approval rules, and command interface remain accepted.

## Context

The original local-review decision defined independently editable notes in repository-local Markdown. The implemented agent handoff then exposed a single interactive flag and required agents to inspect the review file directly. The product direction now treats a review as a conversation: a reviewer creates anchored threads, the reviewer and an agent exchange ordered comments, and the reviewer alone controls thread lifecycle and final approval.

Directly editing the Markdown contract would let agents bypass role restrictions, corrupt lifecycle state, or make approval disagree with persisted state. Keeping reviews only in global private state would prevent a repository-scoped agent from discovering and responding to them.

## Decision

Keep each review as versioned, human-readable Markdown under the repository's gitignored `.reviews/` directory. Evolve the public schema from independent notes to stable threads with ordered, append-only comments.

Each comment records only an author role, `reviewer` or `agent`; individual agent identity is not required. After persistence, neither role edits or deletes an individual comment. Only the reviewer may create a thread, resolve or reopen it, or delete the complete thread with confirmation. An agent may read reviews and append replies only through the non-interactive review command interface.

Threads attach either to a changed file or to a contiguous old-side or new-side textual diff selection. Open and Outdated threads block approval. A successful review exit is possible only after the reviewer explicitly resolves every thread.

Expose review operations through a subcommand namespace:

- `fiew review start [--name <slug>] [--repo <path>]` creates and opens a review;
- `fiew review open <review-id> [--repo <path>]` opens an existing review;
- `fiew review show <review-id> [--repo <path>]` emits stable JSON by default, with optional Markdown output;
- `fiew review reply <review-id> <thread-id> --body-file <path> [--repo <path>]` appends an agent reply without granting arbitrary review-file mutation.

Repository selection defaults to the current working directory. Every new review ID starts with a datetime prefix. An explicit name contributes a sanitized slug; otherwise an interactive start generates a bundled adjective-noun slug. The `.md` extension is automatic, and collisions receive a numeric suffix. Interactive start prints the canonical ID after terminal restoration.

Writes must use atomic replacement, a previous validated backup, schema validation, and future-version refusal. Persistence failure must not produce a successful approval result.

## Rationale

The thread model supports the intended reviewer-agent loop while making authority visible and testable. A narrow command interface gives an agent the operations it needs without granting source writes or unrestricted mutation of review state. Repository-local Markdown remains inspectable and portable, while schema and atomicity rules keep the command result consistent with durable state.

## Consequences

- The next review schema is incompatible with `fiew.review/v1` and requires an explicit migration or read-only legacy behavior.
- The legacy `--review <filename>` interface is replaced rather than extended.
- Existing note edit behavior is removed. Historical comments remain immutable.
- Review parsers must tolerate Markdown bodies without interpreting body headings as structural delimiters.
- Local review writes remain the only repository-local exception to fiew's source-read-only boundary.
- Remote synchronization and GitHub publication remain outside v0.1.
