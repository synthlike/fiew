# Use an explicit current review for routine agent handoff

## Context

Named reviews currently require a reviewer to copy an opaque generated ID to an agent before the agent can show or reply to the conversation. Deriving that ID from staged content would remove the exchange but would also change conversation identity whenever staged work changes, omit unstaged and untracked review scope, and conflate an evolving conversation with one immutable content snapshot.

RFC-0002 established that v0.1 needs only one routine active conversation per repository while retaining explicit historical review access.

## Decision

Persist one explicit repository-local current-review reference under `.reviews/`.

- `fiew review start` creates a review and atomically marks it current.
- `fiew review open` opens current; `fiew review open <review-id>` opens that historical review and atomically makes it current.
- `fiew review show` defaults to current; an explicit review ID accesses history without changing current.
- `fiew review reply <thread-id> --body-file <path>` replies to current; the explicit `<review-id> <thread-id>` form accesses history without changing current.
- Approval does not clear current. Only reviewer `start` or `open` changes it.
- Agent show and reply operations never change current.
- Missing, malformed, or dangling current state fails explicitly. Commands never infer current from content, timestamps, filenames, or directory order.

Opaque review IDs remain the durable identity for storage, history, backups, and explicit commands. Current selection is a pointer to that identity, not a replacement for it.

## Rationale

An explicit pointer removes routine ID exchange while preserving stable conversation identity as code and Git state evolve. Reviewer-controlled updates retain the existing authority boundary. Explicit failure avoids silently sending agent replies to the wrong review, while optional IDs keep historical workflows available.

Content hashes remain useful as immutable snapshot or anchor evidence, but not as conversation identifiers.

## Consequences

- The normal handoff becomes `review start`, followed by agent `review show` and short-form `review reply` with no copied ID.
- Command parsing gains ID-optional open/show and unambiguous one- or two-operand reply forms.
- Current-pointer writes require the same atomic and validated persistence discipline as other review state.
- A dangling pointer is a command failure even if valid review files exist; recovery is explicit `review start` or `review open <id>`.
- Multiple simultaneous current reviews and automatic newest-review selection remain unsupported.
- Existing review IDs, named starts, approval rules, public projections, and historical explicit-ID commands remain compatible.
