# Store review notes as gitignored `.reviews/` Markdown for agent retrieval

> Superseded by [Use reviewer-owned local threads with command-mediated agent replies](<docs/decisions/ARP-0007.md>). This record remains as the history of the original `fiew.review/v1` note model.

## Context

fiew's review notes ([Create and manage local review notes](<.project/issues/ISSUE-0022-create-and-manage-local-review-notes.md>)) are intended for a coding-agent loop: an agent stages changes, a human reviews the diff and leaves comments, and the agent retrieves those comments to plan further work. This makes the review the product's primary output, consumed by an external tool.

The v0.1 specification stored notes as fiew-internal, schema-versioned JSON under the macOS user-data directory, deliberately outside the repository to honor the read-only boundary ("fiew must not write inside repositories or Git metadata"). That location and format are neither discoverable nor parseable by an external agent, so they do not serve the intended consumer.

## Decision

Store review notes as human- and agent-readable Markdown files in a dedicated `.reviews/` directory at the repository root, expected to be gitignored.

Carve out one narrow, explicit exception to the read-only boundary: fiew may create and write files only within `.reviews/`. Every other repository path remains read-only. fiew never edits `.gitignore` or any tracked file, never touches Git metadata, and never modifies source. Ensuring `.reviews/` is ignored is the user's or agent's responsibility; fiew may warn if it is tracked but must not add the ignore rule itself.

Each file is one review. Format (`fiew.review/v1`):

- YAML frontmatter: `schema`, `created`, and `base` (the reviewed ref and its resolved SHA).
- A sequence of notes. Each note is a section with:
  - a cosmetic heading (`path · group/side · Lx–Ly` for line notes, `path` for file notes);
  - authoritative key/value bullets — `id`, `status` (`open`/`resolved`; `outdated` reserved), and `blob` when a side blob exists;
  - for line notes, a required anchored excerpt as a fenced `diff` block holding the exact reviewed lines; file notes omit it;
  - a Markdown comment body.

fiew generates the coordinates, blob, and excerpt from the reviewer's diff selection, so the reviewer only writes the body. fiew reads existing `.reviews/*.md` on open and round-trips them; files are written atomically because an agent and fiew may both touch the directory.

## Rationale

The agent loop needs notes it can find and parse. Markdown in a known `.reviews/` directory is trivially retrievable and parseable, and an embedded diff excerpt plus a side blob SHA let an agent reconcile each note to the exact reviewed content: prefer `git cat-file blob <sha>` when the blob exists, otherwise match the excerpt text against the current file. New-side blobs exist for staged and committed changes — the primary "agent staged its work" flow — and are absent for unstaged working-tree edits, where the required excerpt remains the durable anchor. Reconciliation therefore degrades gracefully rather than failing.

Keeping notes in a single, gitignored, fiew-only directory preserves the spirit of the read-only boundary — no source, tracked file, or Git state is modified — while making the review a first-class, portable artifact. The prior JSON-in-user-data design satisfied the boundary's letter but was invisible to both reviewers and agents.

## Consequences

- The read-only boundary is amended: writes to `.reviews/` are permitted; all other repository paths, including `.gitignore`, remain read-only. This must be reflected in the v0.1 specification's read-only boundary and persistence requirements.
- Notes no longer use the ISSUE-0017 JSON state store or the user-data directory. That store remains for global configuration and trust. Its atomic-write, single-backup, and future-version-refusal discipline still applies to `.reviews/` files.
- The `fiew.review/v1` Markdown schema is a public contract; incompatible changes require a new schema version.
- Line-level notes always embed the excerpt, because unstaged changes have no new-side blob.
- Scope unchanged: cross-refresh re-anchoring and the Open→Outdated transition remain [Re-anchor notes across Git refreshes](<.project/issues/ISSUE-0023-re-anchor-notes-across-git-refreshes.md>); reviewing arbitrary commits stays outside v0.1.
- ISSUE-0022's acceptance criteria change from "outside the repository and `.git`" to gitignored `.reviews/` Markdown that a coding agent can retrieve.
