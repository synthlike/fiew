# Relocate review and bookmark anchors through exact context only

## Summary

Define one conservative anchor transition model for review threads and bookmarks across Git refreshes and source changes. Stable original locations are validated first; relocation occurs only through one exact context match within the same path or an explicit Git rename target.

## Motivation

Review threads currently retain selected diff excerpts, paths, lines, groups, and optional blobs, while bookmarks retain only source coordinates. Neither model can safely distinguish a moved anchor from similar content, preserve reviewer resolution through temporary anchor loss, or update consistently after complete Git refreshes.

ISSUE-0023 requires exact unique relocation, Outdated state on missing or ambiguous content, cross-group thread movement, and no guessed reassociation. Repository-local review and bookmark storage has also made the original global repository reassociation concern obsolete.

## Requirements and constraints

- Validate an anchor at its stored location before searching elsewhere. An exact original-position match is retention, not relocation, and does not become ambiguous merely because identical content exists elsewhere.
- If original validation fails, relocate only on exactly one complete raw-byte context match.
- Line and point anchors contain their anchored content plus up to three complete source lines before and after it.
- Bookmark context also records the selected byte offset within the anchored line.
- Whitespace, line endings, syntax, and encoding are not normalized.
- Path changes are followed only through explicit rename metadata in the accepted Git snapshot. Matching content in unrelated files never moves an anchor.
- Review line threads search all Staged, Unstaged, and Untracked groups within the retained or explicitly renamed path, allowing one unchanged change to move between groups.
- Review file threads use an exact whole-change fingerprint. Text fingerprints include canonical old/new diff bytes, modes, and paths; binary, submodule, and mode-only fingerprints use exact available blobs and metadata.
- A missing or ambiguous match preserves anchor identity and stored location but marks anchor validity Outdated.
- Thread reviewer lifecycle (Open or Resolved) is stored independently from anchor validity (Current or Outdated). While invalid, the public/UI status is Outdated and blocks approval; a later exact match restores the remembered reviewer lifecycle.
- Successful relocation preserves IDs, comments, labels, and reviewer lifecycle while updating only anchor coordinates, group, path after explicit rename, blobs, context, and validity.
- Bookmarks are re-evaluated after every accepted complete Git snapshot and immediately before opening.
- Thread re-evaluation occurs only after an accepted complete Git snapshot, never against pending, stale, partial, or obsolete work.
- Re-anchor transitions use a shared pure matcher and shared fixtures for original retention, unique relocation, ambiguity, absence, group transition, explicit rename, unrelated path, and root movement.
- Git snapshot publication is not rolled back by persistence failure. In-memory transitions remain dirty, failure is reported, and approval or clean quit is blocked until atomic persistence succeeds.
- Moving the entire repository carries `.reviews/` and `.bookmarks/`; repository-relative anchors require no root reassociation and no remote-URL inference.
- New exact context is mandatory in `fiew.review/v1` and `fiew.bookmark/v1`. Existing development records were purged; missing anchor context is malformed, with no migration or compatibility behavior.

## Non-goals

- Whitespace-normalized, fuzzy, heuristic, semantic, AST, or language-server matching.
- Moving anchors to unrelated paths based only on matching content.
- Remote synchronization or remote repository identity.
- Supporting pre-context development review or bookmark records.
- Treating incomplete Git work as an anchor transition input.

## Open questions

None.

## Options

### Option A: Always require one globally unique context match

Simple in principle, but marks an unchanged original anchor Outdated whenever identical content exists elsewhere. This discards reliable location evidence and creates unnecessary review churn.

### Option B: Prefer the stored location, then require one constrained exact relocation match

Validate exact content at the original path/group/location first. Only if it fails, search all Git groups within the same path or explicit rename target and relocate on one exact context. This preserves stable anchors while preventing cross-file guesses.

### Option C: Use fuzzy or semantic relocation

Could follow larger edits and file movement, but introduces scoring, ambiguity thresholds, language dependencies, and guessed matches outside v0.1's trust boundary.

## Recommendation

Choose Option B with mandatory three-line raw-byte context, whole-change file fingerprints, independent lifecycle and validity, and repository-local constrained search.

## Resolution

Accepted by the decision owner for ISSUE-0023. Implement Option B with no compatibility path for purged pre-context development records.
