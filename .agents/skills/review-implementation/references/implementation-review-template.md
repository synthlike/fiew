# Implementation review: bounded scope

## Verdict

Choose exactly one: **Conforms**, **Conforms with follow-up**, or **Does not conform**.

State that the verdict applies only to the scope and evidence below.

## Scope

Identify the implementation issue or settled plan, commit range or working-tree boundary, and included behavior. List explicit exclusions.

## Authoritative intent

- **Specifications:** Agreed behavior reviewed.
- **Accepted ARPs:** Technical constraints reviewed.
- **Issue:** Outcome and acceptance criteria reviewed.
- **Project guidance:** Applicable documented conventions.
- **RFC resolution:** Context only, when relevant.

Record any contradiction that prevents a coherent conformance judgment.

## Implementation evidence

List inspected code, configuration, tests, fixtures, documentation, diffs, commits, and runtime evidence with precise references.

## Verification performed

List exact commands and relevant results. State commands not run and why.

## Findings

### Blocking: concise discrepancy

- **Expectation:** Authoritative requirement and link.
- **Evidence:** Concrete implementation or runtime evidence.
- **Impact:** Material consequence within scope.
- **Recommended disposition:** Smallest next action, not an implicit fix.

### Follow-up: concise improvement

Use only when accepted behavior is present and the improvement is material but non-blocking.

If there are no findings, say so explicitly; do not omit reviewed evidence.

## Limitations and confidence

State unavailable evidence, unrun verification, environment limits, and how they affect confidence. Do not claim that conformance proves no defects exist.
